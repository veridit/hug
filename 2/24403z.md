## Goal
The breadcrumb names the section you came from, and n, p and Esc stay in it, even after the open task moves to another section.

## Purpose
Jørgen 2026-11-20 08:39Z: in ASKED he answers a question, the task rightly moves to another section, and going back up lands him in the wrong section; he asks whether n gives the next task of the old section or the new one, and proposes that the context stays while the task moves.

## Principle
The list you came from is your context; a task leaving it never moves you. One short message says where the task went.

## Relevant details
Jørgen 2026-11-20 10:37Z (crab console): 'When I'm inside a ticket and ... I make some change to it so it moves to another place. I approve something ... and I press next, I get to the previous ticket before the current ticket ... if you had a position and this one is moved, then the next one is the one after this one, not the one before this one ... You have to do that one right.' Rule: the open task keeps its slot in the pane it was opened from even after it leaves; n opens the task that came after it there, p the one before. Code: stepTask (tui.go:1090) moves from m.cursor, which after the reload no longer points at the moved task's old slot (clamp).

crab's reading of main 6fa18387 (unconfirmed, to be proven by a test first): reload -> apply(sn, path) finds the task's new index, then clamp() sees it is not in the current pane and puts the cursor on that pane's FIRST row (tui.go clamp ~1025). The pane is unchanged, the detail still shows the moved task (detailPath). So n (stepTask -> move(+1), tui.go ~1090) likely steps from the first row: it would skip the old neighbour, or revisit the top. Fix: before a reload, remember the open task's pane and its neighbour after it (and before it, for p); when the task has left the pane, set the cursor to that neighbour, so n opens it, p opens the one before, Esc lands on it. The detail header shows 'moved to IN PROGRESS'. Keys provisional (bfxq93).
