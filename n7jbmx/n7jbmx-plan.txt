THE SIGNAL: exact anchors, not text similarity
- A tool call yields anchors: repo-relative touched paths
  (JCODE_HOOK_TOUCHED_PATHS) plus their basenames, and for bash the command
  head (first 1-3 words of each pipeline step: `hug task done`,
  `git rebase`, `go test`, `sqlite3`).
- A memory yields anchors at index time, extracted locally with no model call:
  paths, file names and backticked commands in its text. A table
  anchors(unit_id, kind, value) stores them. When jrj1vq lands, its CASE
  paths/tools feed the same table. That is the "CASE from when-then fields"
  part of check 2. Until then local extraction stands in, so ruling needed:
  is that acceptable for check 2?
- The trigger fires when at least one anchor matches exactly (a path suffix of
  2 or more segments, a basename only when rare, a command head) AND the
  memory's type is rule, fact or preference (records were 8% precise) AND it
  is in a visible scope. Rank by anchor rarity (IDF over the store). Show at
  most 2 per call, each memory at most once per session, never one already
  shown this turn.
- Local and free: SQLite lookups only, no embedder in the hook. The p95
  target is under 200 ms in a fresh hook process.
