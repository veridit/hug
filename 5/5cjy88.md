## Goal
In / search, Enter leaves you on the results where j/k and Enter work; Esc there returns to the full view on the task you picked.

## Purpose
Jørgen searched k5q120, the wrong task was picked, the arrow keys did nothing, and Enter jumped back to the board on that wrong task.

## Principle
Typing narrows, Enter commits to the results, Esc steps back one level: before Enter it cancels, after Enter it leaves the results keeping your pick.

## Relevant details
Jørgen 2026-11-21 08:34Z, statbus board, v0.7.93, typing '/ k5q120': the selected row was hmgadt (RECENTLY DONE), whose notes mention k5q120, while k5q120 itself sat in LINT. Footer: 'found hmgadt, row 15 of 599 in RECENTLY DONE'. Causes on main f2da2991: (1) the arrows never reach the search: tui.go:1926 historyKey runs before updateSearch (tui.go:1929), so ↑↓ recall search history instead of picking (search.go:29-32 is dead for ↑↓); the footer still says '↑↓ pick'. (2) searchTyped (search.go:45) keeps the current pane when it has any match, so a task whose id is typed exactly loses to a task that only mentions it. (3) Enter is leaveSearch(false) (search.go:34): it clears the search at once (mcvfbz's rule from 2026-11-16), so there is no results screen to walk. New flow, Jørgen's words: 'escape before enter is cancel the search ... escape after enter would be stay on the ticket, go out again'. So: typing narrows and picks the best match; ↑↓ (and ctrl-n/p) pick among matches; Enter closes the prompt and leaves the results shown, where j/k, Enter (open), m/J/K work; Esc there clears the search and keeps the picked task selected in the full view (mcvfbz's keep-the-task rule still holds); Esc while still typing cancels and returns to the task you were on before /. Tab (keep as filter) becomes the same as Enter, so it can go or stay: crab's proposal is to drop it. Keys provisional (bfxq93).
