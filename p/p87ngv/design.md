# p87ngv design: inline marks

The full design text as it stood on 2026-11-20 10:42Z, moved out of the ticket so the ticket reads short (Jørgen request 6).

## Goal

People and agents mark a task's text inline, and each mark resolves into clearer ticket text, its dialogue kept aside.

## Purpose

Jørgen 2026-11-19 08:55Z: attach a request to a piece of the text in a mark mode, so the AI knows exactly what it is about; questions today look like acceptance criteria. 09:05Z (answer 1 on this task): threads inside the ticket would bloat it, and the conversation must not become the thing. The ticket must stay crisp: clarity comes from boiling text down to its essence. The messy part goes to a separate, suitably named history file in the task's files (provenance, chat history) that grows by appending.

## Principle

Ticket = working document, short and current. History = append-only provenance file, linked from the ticket, never needed to understand the ticket. Marks are plain text in the field they are about, so git, grep, any editor and any agent see them. Resolving a mark means changing the ticket, not adding to it. The agent instruction: lead with clarity in the ticket, answer and act on marks, post new questions as marks, move the dialogue to history. Reuse an existing markup convention for the sigil if one fits. Either side may resolve a mark (Jørgen 09:05Z): the person accepts, approves or asks for something else; the agent judges by the ticket whether the mark is answered. Both use judgment, and either can initiate a resolve for clarity. Anchors (Jørgen 09:06Z): a mark may sit on anything in the ticket's markdown, or point into an attachment by name plus line or section ('in mock-100x30.txt, line 12'); the attachment itself is not edited. Dialogue never enters the ticket; the history may be split per thing discussed. SeidDataMarkdown is entirely passive (Jørgen 11:38Z): embedding only, never executed; hug scans and shows marks, people and agents act on them. Marks (Jørgen 11:39Z, crab's wording approved): the pieces of SeidDataMarkdown are called marks (.Request, .Question, .Comment, .Answer); files stay .md. Four properties: (1) passive: marks embed data and are never executed; people and agents act on them. (2) readable raw: a ticket with marks reads right as plain text in any editor, grep or Markdown viewer. (3) self-ending: no closing delimiter; a mark ends at the first token that does not start with a dot, so a broken mark cannot swallow the ticket. (4) transient: a mark lives until resolved; a finished ticket holds no marks, and what they said moves to history.sdo. Who writes what (Jørgen 11:47Z): people write loose text anywhere in a ticket or attachment, no syntax needed; the agent reads the diff and turns each loose comment into a structured mark (or acts on it at once), and only agents write and lint marks. A person may still type a mark; it is linted the same way. Why (Jørgen 11:48Z): this turns unstructured input into structure that hug and agents can reason about and act on in a structured way: list, count, deliver, lint, resolve.

## Details

The ticket stays the crisp working document. A person or agent marks a piece of a task's text with a comment, question or request that sits inline in the text, visible as text, with a recognizable sigil. The agent picks marks up, acts or answers, and resolves each by rewriting the ticket text to the clarified result and removing the mark. The dialogue that led there (the mark, replies, who and when) is appended to a history file attached to the task, never kept in the ticket.

Syntax (Jørgen 09:31-09:35Z, console): Seid things. A mark is a thing, space-dot-Capital, followed by its lowercase properties: .Request .by:jhf .at:2026-11-19T09:40Z .msg:"Can you shorten this?" Kinds: .Comment, .Question, .Request; replies are further things in the same run (.Answer .by:crab .at:... .msg:"..."). Properties: .by, .at, .msg, .on:"quoted words" (the span; without it, the sentence before the mark), .in:"NAME#line" or "NAME#section" (a pointer into an attachment). The run ends where prose resumes (a word without a leading dot). Span delimiters in the text (.( ... ).Request, .{ ... }.Comment) were considered and rejected by Jørgen 09:35Z: they break Markdown. Board scan 09:31Z: space-dot-Capital occurs 9 times in all task files (.Compiler 6, .Oject1, .Object2, .Feature), none a mark kind; lowercase dotfile paths (.hug, .md, .backlog) can never start a mark. History: each task's history.sdo in its folder (Jørgen 09:35Z), hug's own Open-data variant (.sdo, Jørgen 11:07Z; Seid's Open tier is unfinished) (.Uppercase constructors, .lowercase properties, seq ... end), append-only; on resolve the agent rewrites the text and appends .Resolved .at:... .was:"..." .now:"..." .marks: seq <the run> end. Also set aside: CriticMarkup (wraps prose in brackets), bare inline properties (a property needs a thing). Replaces ## Questions and ## Requests over time (q2adr8, hbgybn); open marks show in ASKED and requests as those do now; delivery as gmzd87. TUI: a mark mode in the detail view selects a span; c comment, ? question, r request; open marks drawn calmly (qh9ep1 check 9), a key jumps between them. Anchors by structure (Jørgen 09:44Z): .prev:.Sentence means the sentence just before the mark, with no quote to go stale; likewise .prev:.Word, .prev:.Paragraph, .prev:.Item (a list item or check). .on:"quoted words" stays for a span inside it. With neither, the mark means .prev:.Sentence. Example: Make it concise. .Request .by:jhf .prev:.Sentence .msg:"Make it concise" Parsing rule (Jørgen 10:22Z): a constructor as a value stands alone. In .prev:.Sentence .msg:"..." the .msg belongs to the mark, not to .Sentence. A value with its own properties is parenthesized: .prev:(.Sentence .n:2) means the second sentence back. The giveaway (Jørgen 10:23Z): ':.' followed by a capital letter is a constructor value (.prev:.Sentence); ' .' (space-dot) followed by a capital letter starts a new thing in the run (.Request, .Answer). A scanner needs only those two cases. Ending rule (Jørgen 10:24Z): everything that continues a run starts with a dot (a property .x:, a value :. or a thing ' .Capital'); the first token that starts any other way ends the run, and prose resumes. Hard-to-quote text (quotes, several lines) goes in a triple-quoted string: .msg:"""he wrote "true" here
and on a second line""". The opener is """ and the closer is the first """ not followed by another quote, so a closing quote inside the text may touch the delimiter (""""). Seid's SYNTAX.md has no triple-quoted string yet (rg '"""' found none, 10:25Z); this is hug's rule until Seid defines one. Rulings on the mock (crab 10:31Z, from MOCK.md into the ticket 11:35Z): mark numbers are display only, in text order; CLI --on is the span (.on), --near WORDS finds the unit; resolve needs --now TEXT or --keep; .Resolved keeps .by .field .check .msg; an .in: mark sits at the end of ## Notes; hug writes marks verbatim, no escaping. Not Seid-parsable, by design (Jørgen 11:37Z): Seid quotes text inside code with {{ ... }} (design/Kernel-Seid.md section 2b); a ticket is the inverse, Markdown text with data blended in, and the marks are acted on, then removed. So the mark grammar is hug's own, defined here; a whole ticket is never fed to Seid. history.sdo is pure data and may follow Seid's Open tier once it exists. Name (Jørgen 11:37Z): SeidDataMarkdown, Markdown where data is a piece of the text itself. The mark grammar in these details is its first definition; hug owns it until Seid takes it up. Edits are the notification (Jørgen 11:47Z): when hug tui gets back from the editor on a task file or one of its files (editFiles, files.go:141-158; editorMsg, tui.go:1330), it already re-lints and commits; it then diffs that commit, and if the diff adds text (new marks, or any added lines in an attachment) it delivers to the assignee or coordinator as a request does (gmzd87), naming the task, the file and the commit, so the agent reads the diff. Edits outside hug: on the next hug command's sync, a new open mark found by the scanner is delivered the same way.
