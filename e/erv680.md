## Goal
Any agent opening hug is told the one step due now for its role (worker, reviewer, coordinator, person), with the command to run.

## Purpose
Jørgen 2026-11-26: the system must tell you what to do when it is due, whatever the agent or its instructions; nobody should have to know the process a priori.

## Principle
hug derives the next step from the task's state; nothing is memorised. One step at a time, with its exact command. A cue appears only when that step is due, and disappears once done. Same text in the CLI next: line, the MCP result and the board cue (boardcue.go). hug names the stage, never a project's procedure: how to ship comes from the project (AGENTS.md or a hug.toml ship line), so the same hug works for a project that tags releases, deploys, or only merges.

## Details
Cues today (muninn/internal/recall/boardcue.go:341-374): request, answer, answered, owner, done (every check holds), work (working on a task that is not doing), take (changing code with no task). Missing, in lifecycle order: (1) a task is taken with no acceptance checks: 'write its checks: hug task set ID --accept ...'; (2) a worker's checks are all ticked: review starts by itself (5yh7hr); (3) a reviewer approved: 'land the tested SHA, then release'; (4) released: the person's checks are asked (exists, afterrelease.go); (5) a check is ticked without evidence: 'add the evidence'. Open design question for Jørgen: acceptance checks and work items one list or two (b6wtwa: checks are the smallest pieces).
