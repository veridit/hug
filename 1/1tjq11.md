## Goal
Scrolling, typing and moving in a task's page answer within 50 ms per key, even on a 700 KB task with 759 notes.

## Purpose
Jørgen 2026-11-22 21:37Z and 21:49Z: answering inside a task is SUPER SLOW, and in Seid even scrolling p39w4a is extremely slow (screenshot: NOTES (759)).

## Principle
Work done once per task change, not once per key: parse, sections, links, id stops and the focus ring are computed when the task or the width changes and reused for every key and frame until then. Measure before and after on a copy of the real board.

## Details
Measured by crab 22:09Z on a copy of seid-lang's board (v0.7.108 code, origin/main 6b8899ba), go test probe, 180x50, load ~30-80:
- p39w4a (668,041 bytes, 1012 lines, 759 notes): open 1.05 s; one j: p50 769 ms, p90 1.34 s, max 1.45 s; View alone 164 ms; syncDetail 108 ms; idStops 86 ms; detailText 99 ms.
- qrpkzm (207 KB): one j p50 175 ms, p90 375 ms.
- hug's own board (hd74ct, 4-15 KB tasks): one key in the request box p50 4-8 ms (fine). Real tui in tmux: 23-87 ms per key, at load 65-80.
CPU profile of 10 j presses on p39w4a (pprof -focus model.step|View): model.links 0.56 s -> sections (re-cleans and splits the whole file) + taskRef regexp over all text; keyBar -> detailHints -> focusRing 0.49 s -> idStops (regexp ids and fileWords over every text); markedBlock 0.43 s (detailText again, ansi.Strip, split); folds 0.22 s. Each key builds the page several times; nothing is cached across keys.
Not the cause: hug tui processes use 1-3% CPU idle and write about 3 KB per 5 s to the terminal; the machine load is from a VM, Docker, Safari and Codex.
Probe to reuse: a test that opens p39w4a on a board copy (rsync of git ls-files into a scratch dir, git init) and times press j + View; delete it after.
