## Goal
Each release is one ticket that groups what it ships and asks the owner, one question each, whether it works for him.

## Purpose
Jørgen 2026-11-19 11:18Z (crab console, RECENTLY DONE showing Release v0.7.78..81 as bare chores): he cannot see which tickets are in which release, and shipped tickets that ask him to confirm are lint errors (shipped-not-done: 5 at 11:18Z, 0gztsy a6xm8n b5jks7 p277bp txjkrm; 40 doing tasks carry a 'shipped in' note). He proposed closing shipped tickets and asking him about the release as a group. 11:20Z: one ticket per release (group plus feedback), 'let's try that out'.

## Principle
One release ticket = the group and its feedback. Membership comes from git (deduce already maps tags to tickets via commit subjects), never typed by hand. Questions are about what shipped, one per ask, each naming its ticket. Lint: an asked release ticket is fine; a non-release ticket with open checks after it ships is still an error. Migration changes no text in old tickets beyond moving their owner-confirm checks to their release's ticket (struck with a reason pointing there).

## Relevant details
A ticket closes when its work ships; its checks hold only what the worker can prove (tests, CI, goldens). Each release is one ticket: the parent of every ticket it contains, linked by hug when the tag is cut, and the place where the owner is asked, one question each, whether the shipped changes work for him. It stays asked until he has answered, then is done. A no becomes a new bug linked to the original ticket and the release; the original stays closed.

Pieces: (1) hug task deduce / release step sets --parent RELEASE on each ticket a new tag contains (release ticket found or created by title 'Release vX.Y.Z'); hug task ls --epic RELEASE lists them; TUI shows the children under a release. (2) Owner-confirm checks: help, AGENTS.md section and worker instructions say they go on the release ticket as asks, not on the ticket. (3) lint: shipped-not-done does not fire on release tickets; its fix names moving the check to the release ticket. (4) Migration for the 40 shipped doing tasks: move each open 'Jørgen confirms' check to an ask on its release ticket, strike it on the task with a pointer, done the task if nothing else is open. (5) crab's release procedure from v0.7.82: release ticket gets its children and one ask per shipped change. Related: gpyqq9 (ask settles shipped-not-done), deduce.go:101-153, q2adr8 (several questions).
